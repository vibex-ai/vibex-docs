title: "Privacy and recovery"
description: "Understand Vibex's local storage, restart recovery, backup approach, and diagnostic data boundaries."
---

Vibex is local-first: the authoritative runtime stores projects, workspaces, sessions, timelines, provider profiles, terminal metadata, browser profiles, computer-use audit data, routing ledgers, and remote device records. Remote connections receive only authorized projections.

## Where data lives

| Data | Location |
| --- | --- |
| Authoritative metadata and session state | SQLite database under the runtime home |
| Project files | The local directory you chose, or a Vibex-managed Git worktree |
| Provider credentials | The OS keychain; a headless host falls back to an owner-readable secret file |
| Agent installations | The runtime home |
| Browser profile | An isolated `user-data-dir` under the runtime home; imported login state lives there too |
| Computer-use records | Redacted audit records under the runtime home; no screen pixels or typed text |
| Gateway request ledger | The runtime database; tokens, latency, status, and routing metadata only |
| TUI preferences | `~/.vibex/tui-interface.json`, `~/.vibex/tui-keys.toml` (or the matching home) |
| SSH / WSL connections | `ssh-connections.json`, `wsl-connections.json`, and the remote runtime registry under the desktop home |
| Relay data | **None**. The Relay forwards encrypted frames and stores no business database |

Relay rooms and connections are transient. Relay logs should contain routing, counts, and timing metadata only.

## What survives a restart

After a restart, the runtime reloads workspaces, sessions, and configuration from durable records:

**Kept (SQLite or runtime home):**
- Projects, workspaces, and workspace modes
- Sessions, timeline events, messages, goals, delegation relationships, and archive state
- Provider profiles, shared Providers, route groups, MCP servers, Skills, and Prompts
- Terminal **metadata** (tab names, bindings)
- Unsent composer drafts and scheduled sends
- Browser profile and imported login state
- Remote device grants and SSH/WSL connection profiles
- Workbench background, themes, and TUI preferences

**Not kept (memory only):**
- Running Agent processes
- Terminal **contents and scrollback**
- Open browser tabs and live frames
- Active connections and live event subscriptions
- An in-progress computer-use session

<Info>
  `running` in the database is only the **last observed state**, not proof that a process is alive. After a restart, verify the process before retrying.
</Info>

A lost terminal is marked `stale`. Use the new terminal snapshot; do not replay commands from the old one.

## Device revocation

Revoking a device in the authority's device list immediately closes its active connection with `device_revoked`.

- Reuse requires **pairing again**.
- Old QR codes, connection strings, grants, and tickets are invalid.
- Revocation is written to the device audit record.
- An SSH/WSL runtime is reachable only through the desktop tunnel; phones cannot pair with it directly.

## Diagnostic data

**Settings → Data & Diagnostics** can clear diagnostic data. The current release has no user-facing diagnostic export page; if you export a bundle through developer tooling, check the redaction first:

**Must be removed:**
- Tokens, private keys, pairing codes, and connection strings
- Full prompts and file contents
- Git diffs and raw terminal bytes
- Browser cookies, localStorage, and login state
- Computer-use typed text, clipboard contents, and screenshots

**Safe to keep:**
- Version, channel, and platform
- Structured error codes
- Redacted timestamps
- Non-sensitive resource ids

<Warning>
  Diagnostic export is **one-way**: once posted publicly it cannot be recalled. Read it yourself before uploading.
</Warning>

## Backup

Vibex does not currently provide a one-click backup button. The reliable approach is to back up the entire **runtime home**:

1. Stop the runtime using that home (desktop, TUI, or headless server).
2. Copy the whole home, including `vibex.db`, `vibex.db-wal`, `vibex.db-shm`, identity keys, Agent installs, browser profile, and credential references.
3. To restore, place the backup in an empty directory and point the runtime at it.
4. After restoring, check workspace paths, device grants, and provider credential references.

<Warning>
  Copying only `vibex.db` without WAL/SHM can produce an inconsistent database. Do not copy the database while the runtime is writing to it.
</Warning>

A headless runtime stores data under `/data` by default; mount it as a persistent volume or sessions disappear when the container is recreated. An SSH/WSL runtime stores data under `~/.local/share/vibex/server` in the remote home.

## Import data from a release candidate

Stable and RC are separate applications with their own application identity and data directory (`desktop-stable` and `desktop-rc`), so a stable install starts empty.

To carry RC work forward, open **Settings → Data & Diagnostics → Local storage → Import RC data** and confirm:

1. Vibex snapshots the RC database.
2. The snapshot is migrated to the current schema and the copy is verified.
3. It is swapped in on the next start; workspaces, sessions and Provider configuration come with it.
4. If the import fails, the current data is kept and nothing is imported.

On the first launch, RC data sitting next to the stable install also raises a one-time prompt offering **Import data** and **Not now**. The RC install itself is never modified, so you can keep using it as a fallback.

<Warning>
  **The import runs one way: RC to stable.** Do not copy a stable database into an RC directory; their schemas may not agree.
</Warning>

## Cleanup

**Settings → Data & Diagnostics** offers per-category cleanup: sessions and attachments, terminal data, and diagnostic data. These actions **cannot be rolled back**.

Browser data can be cleared separately under **Settings → Browser → Clear browser data**. Computer-use records and the gateway ledger stay with the runtime data unless you clean the corresponding database.

<Warning>
  Resetting settings only affects preferences. Deleting the database, data directory, or workspace directory is a different, destructive operation. Confirm you no longer need the data first.
</Warning>

## External service boundary

Agents, MCP servers, shared Providers, and browser pages may send the context you explicitly provide to a provider or external service. Read the service's privacy policy, and limit data with the smallest scope, permission approvals, and minimal attachments.

Pairing with a remote authoritative runtime means **that runtime's administrator can see your session data**. When you self-host, that administrator is you; confirm this before connecting to someone else's runtime.
