title: "Agent sessions"

A session stores the input, Agent output, and tool activity of one development task as a structured timeline. The **authoritative runtime** holds the authoritative timeline; other clients only display its projection.

## Create a session

1. Choose the target project and location (**Local**, **New Worktree**, or **Temporary session**—see [Projects and workspaces](/en/workspaces)).
2. At the far end of the workspace row, choose the **transport**: **Vibex interface** (the default, where Vibex draws the GUI timeline) or **Native terminal** (where the Agent's own CLI owns the conversation inside a PTY). See [Terminal mode](#terminal-mode).
3. At the top of the composer, choose the Agent, provider profile, model, **Thinking depth**, **Conversation mode**, and the built-in tools available to this session.
4. Enter your task. Use `/` to pick a command or Prompt, `@` to reference a workspace file or an Agent, `$` to insert a Skill, or `↑` / `↓` to recall an earlier message from this session; you can also add attachments.
5. Confirm the workspace and permission scope before sending. The Agent may need to read files, run terminal commands, or request extra authorization.

Switching Agent or model only affects later runs. Messages already written to the timeline keep their original run identity.

<Note>
  A **temporary session** belongs to no project and is useful for one-off questions or prompt tests. It is still stored by the same runtime, can be archived, and cannot create a worktree. The sidebar, its context menu, the new-session picker and search all read "Temporary session", with a green sparkle resolved rather than stored as its default logo.
</Note>

## Terminal mode

Terminal mode hands the session to the Agent's own command-line interface: the conversation happens in a native PTY, and Vibex stops drawing a timeline. Use it when you already know an Agent's TUI well, or need something only that CLI offers.

| | **Vibex interface** | **Native terminal** |
| --- | --- | --- |
| Who draws the conversation | The Vibex timeline | The Agent's own CLI |
| Vibex extensions (goals, delegation, approval cards, queue, scheduled sends, usage) | Yes | No |
| Session row, search, notifications, mobile, TUI | Yes | Yes, on the same row |
| Credential source | Provider profile or Agent account | **Provider profile only** |

Thirteen Agent CLIs are verified: Claude, Codex, OpenCode, Gemini, Pi, Grok, Cline, Copilot, Cursor, Kimi, CodeBuddy, Devin and Hermes. An Agent with no terminal mode does not show the switch at all.

How it behaves:

- The new-session draft is passed to the CLI as its positional prompt, and attachments follow as paths, so the Agent starts on the turn you already described.
- The configured model rides the command line; an Agent default passes nothing rather than a guessed id.
- Terminal mode carries a **provider profile** only. When the page has no profile to hand over, the switch's tooltip says the CLI will use its own login.
- The session row still reports the Agent's activity, unread state and notifications, drawn from the observation facts Vibex records outside the terminal grid. When a reading is unavailable the state is unknown rather than guessed as idle.
- A session whose process ends is closed and marked as an error; a restart re-offers the same argv, working directory and provider profile, and rebuilds the PTY from the recorded argv.
- MCP servers, Vibex delegation, the embedded browser and computer use reach the CLI through the launch input it actually reads, with credentials kept out of the command line. Agents with no per-process MCP input (Cursor, Gemini, Grok, Kimi Code, Devin) show both tool panels as unavailable.

<Warning>
  Terminal mode has no Vibex approval cards. The Agent CLI's own permission prompts are answered in the terminal, and Vibex does not confirm them for you. Stopping a session also does not undo external work already done.
</Warning>

## Reading the timeline

| Item | What you see |
| --- | --- |
| User and Agent messages | Markdown text, images, and attachments. |
| Reasoning | A reasoning summary you can expand or collapse. |
| Plan | Todo steps and their progress. |
| Tool and process details | Tool name, argument summary, process and exit result, and a **{n} process events** count. |
| Permission requests | Actions waiting for your approval or denial. |
| Elicitation forms | Typed forms the Agent needs you to fill in. |
| Delegation | Child Agent or delegated-task state and result. |
| Goals | Goal phase, statistics, and controls. |
| Status events | Running, queued, waiting, completed, failed, stopped, and reconnected. |

A turn shows its **Worked for** duration. While generating it shows **Thinking...** or **Waiting for confirmation...**. Settled turns fold; the transcript reads a bounded window and paging older history does not move your place.

Right-click a user message, Agent answer, selection, process row, turn header or the timeline to open a menu: copy, quote into the composer, fork at the row, edit and resend, stop a streaming answer, or copy a process row's command, output, input, diff or path. A selection can be copied as text or Markdown, quoted, found, and used to open one external link. A selection inside a row takes priority over that row's menu; a menu opened on a group pane or the read-only child Agent rail acts on that transcript, and the child rail keeps copy and quote only.

**Settings → Session** has **Auto-collapse tool calls**, off by default. With it on, a live run of tool activity draws only its one-line summary — changed files, commands, reads and failures — and you open the run to see the calls; a run holding an approval-pending row stays live.

Tool arguments, terminal output, and file diffs may contain sensitive content. Review and redact before sharing diagnostics.

## Session groups and split panes

A session group collects several sessions under one worktree, useful for several Agents or branches of one task:

- Multi-select sessions in the sidebar and choose **New session group**.
- **Split pane** to view members side by side, or **Merge panes** to return to one view.
- The group header shows team state: running, waiting for approval, completed, or failed.
- **Auto continue** can be enabled for the whole group.
- Drag a group into a folder, swap it with another group, or drag it back to the workspace root; drag a member within the group to reorder, or out to remove it.
- **Dissolve session group** does not delete the sessions.

A group can only contain sessions from one worktree. Use several groups for several worktrees.

## Goals

Agents that support goals publish them over ACP: the generic `_meta.goal` extension and Codex's older `_meta.codex.goal` namespace. Vibex normalizes both into one model and stores every change as a goal timeline entry.

The goal bar sits above the composer, directly below the queue:

- It shows the phase, the goal, and the Agent's own statistics (elapsed time, token usage, turn count).
- The pencil button (**Edit goal**) opens an in-place editor; saving goes through goal control, not the composer.
- **Pause goal** / **Resume goal** pause or resume it.
- **Clear goal** clears it; running, paused, blocked, and quota-limited goals can all be cleared.

Buttons appear only when the adapter explicitly declares support. A `/goal` message keeps its own bubble with a goal icon at the edge.

## Delegation and Agent teams

A delegated task has a lifecycle:

- **Keep open**: the child session survives after the round and accepts follow-ups.
- **Accept**: confirm the result; a retry resolves to the original acceptance instead of overwriting earlier work.
- **Cancel**: permanent; it blocks new messages and new child work anywhere under the task.
- **Follow up**: only a task that actually ran can be followed up; a changed intent is refused.

The UI shows:

- The sidebar **ownership tree**: child sessions hang under the parent with a tree guide.
- The session group's **team status header**: how many child Agents are running, waiting, or done.
- A **delegation card** that locates the child pane.
- The `@` menu split into **Files** and **Agent delegation** tabs, each row saying what it names.

A child Agent has its own timeline, reachable from **Child Agent timeline** in the right rail. A child's generated title never replaces the root session title.

## Control a run

| Action | Description |
| --- | --- |
| **Stop current reply** | Stop the run. Files and commands already executed are **not** rolled back. |
| **Continue** | Send another task in the same session. |
| **Retry** | Re-run a failed turn according to the Agent's retry semantics; check external side effects first. |
| **Fork session** | Branch from the current timeline or from a sidebar row; useful for comparing two approaches. |
| **Rename** | Change the title without changing the Agent context. |
| **Edit message** | Rewrite the last user message; completed timeline events are not rewritten. |
| **Archive** | Remove the session from the sidebar while keeping its timeline; restore it under **Settings → Archived sessions**. |

<Warning>
  Stopping an Agent stops the run; it does not undo files, Git, or external-service changes. Check the Git diff and the terminal separately.
</Warning>

## Queue, steering, and scheduled sends

Messages sent while a turn is running go into the queue. The queue area above the composer offers:

- **Automatic** / **Manual** sending.
- **Steer**: only for Agents that declare native steering; it injects the message into the running turn instead of interrupting. Other Agents fall back to interrupt and resend.
- **Schedule send**: pick an hour and the message waits in the queue; the schedule survives restarts, can be edited in a popover, and is visible to other clients.
- **Send queued message**, **Edit queued message**, **Delete queued message**.
- **Resume queue** / **Clear queue**.

The delivery mode is recorded on the user message and rendered as a reaction at the bottom of the bubble: **Steered the running turn** (primary) or **Interrupted the previous turn and resent** (warning). When a newer turn exists, the older one is marked superseded: live state, duration, and streaming expansion stop, but rows already produced stay visible and expanded.

Deleting or cancelling a queue item does not undo work already done. A scheduled send still respects session state and permissions; if the session is waiting for approval, the send waits rather than skipping it.

## Auto-continue

With **Auto-continue** on, only turns that satisfy session settings and Agent capabilities advance automatically. It stops at permission requests, elicitation forms, failures, or choices that need a human.

- It is on by default and can be changed under **Settings → Session**.
- A session group can enable it for the whole group.
- During the countdown, cancel the current continuation from the UI or with `t` in the TUI.
- Auto-continue never bypasses permission approval or answers an elicitation for you.

## Permission requests and elicitation

When an Agent requests the terminal, a file write, browser navigation, computer use, or another protected capability, the timeline shows the reason and scope—working directory, arguments, environment. The choices are **Allow**, **Deny**, and **Always allow for this session**.

An elicitation form asks for structured input. Confirm values and scope before submitting; cancelling returns a cancellation to the Agent, not an implicit approval.

A computer-use approval card also names the target application, action class, and reason; destructive or foreground actions carry a screenshot. Password managers, secure fields, and Vibex's own windows are handled per action or hard-denied.

## Global search and find

`cmd-k` opens **Global search** (the workbench command palette) anywhere; the entry point is the search icon in the title bar, just before the runtime control. One query searches three groups:

| Group | Scope | On selection |
| --- | --- | --- |
| **Recent sessions** / **Sessions** | Session titles and message bodies | Open the session and jump to the matching message |
| **Settings** | Settings options | Open Settings, locate the section, and highlight the row |
| **Quick actions** | Real workbench Actions | Run directly; each row shows its shortcut and disables when a precondition fails |

- The panel has its own query field and separators between groups; an empty query lists **Recent sessions**.
- Session search indexes and highlights conversation text only—user messages, Agent replies, reasoning, and plans—and colors only the matched keywords, with the current hit stronger.
- With a non-empty query, `escape` clears it first, then closes on the next press.
- The index builds in the background and stays warm; archived sessions are not searched.

Use `cmd-f` for **Find in current session**.

## Import local history

Use **Import sessions** from the sidebar's **More** menu or a project's context menu.

Fourteen sources are supported: **Claude Code**, **Codex**, **OpenCode**, **Gemini CLI**, **Cline**, **Hermes**, **CodeBuddy Code**, **Kimi Code**, **Pi**, **Grok**, **Cursor**, **DeepSeek Harness**, **ZCode**, and **Google Antigravity**.

1. Vibex scans local history and shows **Scanning local Agent sessions...**.
2. Select sessions in the preview, grouped by project; filter by Agent or rescan.
3. Click **Import {n} sessions** and wait for **Import complete**.

Results are grouped into **Imported**, **Gone**, **Failed**, and similar states.

<Note>
  The scanner reads metadata only: title, time, workspace path, message count, and source path. Content is read only when importing and written to the timeline once. Credentials, keys, and the full Agent home configuration are **not** imported. An already imported session is not imported twice or overwritten by a refresh.
</Note>

## Notifications and unread state

When a session completes, fails, or needs input, the authoritative runtime can send a desktop notification. The three kinds can be toggled separately under **Settings → Session → Agent notifications**.

A session with an unread completion shows a dot in the sidebar; opening it clears the dot and the authoritative timeline wins. The tray menu also offers **New session**, **Config Center**, and **Settings**.

## Archive and restore

Archiving keeps the full timeline and only removes the session from the sidebar:

- Archive from a session row menu, the multi-select menu, or the bulk bar; it is reversible, so no confirmation appears.
- **Settings → Archived sessions** restores or permanently deletes.
- Automatic archiving can be set per project/folder to an idle window (off, or 1–14 days).
- A mistaken archive can be undone; a delete cannot.

## Child Agent timelines

When a session delegates, the right rail shows a **Child Agent timeline** entry. A child has its own timeline, and its updates are attributed so they never fold into the parent's rows.

## Continue in the terminal

The Vibex TUI attaches to the same runtime and reads the same sessions, sends messages, handles approvals, and manages the queue. `vibex` opens the new-session page for the current directory; `Ctrl+L` opens the session list. See [Vibex TUI](/en/tui).
